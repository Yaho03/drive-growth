# 프로젝트 진행 계획

제품은 [PRD](01_PRD.md), 데이터·호출 경계는 [기술 계약](02_SYSTEM_ARCHITECTURE.md), 실행 결과는 [검증](06_VERIFICATION.md)을 기준으로 한다. 기획은 전원이 결정하고 구현은 기능별로 나눈다. 진행 상태는 GitHub 이슈 라벨로 관리한다.

## 1차 제출 앱 구현의 현재 실행 방식

2026-11-09 사용자 결정: 1차 평가에 제출할 앱과 실제 동작의 완성을 우선하며, 남은 구현·수정은 환석이 책임지고 기존 작업 세션에 나누어 진행한다. GitHub assignee는 변경하지 않는다. 아래 기존 담당표는 할당 이력·영역 경계로 보존하고, 기존 담당자의 답변이나 직접 구현을 기다리는 선행조건으로 삼지 않는다. 메인 작업이 구현·독립 검증을 순서와 공유 파일 경계에 맞춰 배정하고, 조율 담당 한 곳이 검증된 정확 head의 PR·일반 main 머지·연결 이슈·README/관련 문서·원래 로컬 동기화를 담당한다. PR 일반 댓글·리뷰·줄 댓글과 이슈 댓글의 구현/수정 요청도 태그된 사람과 무관하게 환석의 위임 작업으로 수집해 메인에서 배정한다. 원문 작성자·기존 assignee·실제 실행자의 근거는 바꾸거나 가장하지 않는다.

기존 확정 규칙과 명시 시험값을 유지하고 경제 밸런스 미세 조정·상용 배포 정책 논의는 현재 앱 연결의 선행조건으로 추가하지 않는다. 의미가 미정인 부분은 실제 미지원 또는 명시한 시연 입력으로 구분하며 정상 권위·지급·실차 입력을 임의로 만들지 않는다. 원자 확정·중복/누락·실패 보존·주행 제한·저장/재실행 검증은 계속 적용한다. 실제 구현·SQLite·제품 UI·에뮬레이터/실차의 근거를 구분하고 게시·리뷰 기준은 [CONTRIBUTING](../CONTRIBUTING.md)을 따른다. 이 결정은 GitHub assignee 변경, 제품 기능 제외, 외부 문의/최종 제출 허가를 뜻하지 않는다.

## 새 팀원이 시작하는 순서

1. README의 현재 구현 범위를 읽고 [개발환경](05_DEVELOPMENT_SETUP.md) 명령으로 같은 버전의 테스트·빌드를 실행한다. 실패는 #12에 OS/CPU·명령·오류 단계로 남긴다. 다른 사람의 로컬 SDK 경로를 복사하지 않는다.
2. CONTRIBUTING과 자신의 구현 이슈를 읽는다. 이슈의 포함/제외, 수정 영역, 필요한 계약, 시작 조건, 기대 결과를 확인한다. 전체 준비 이슈의 종료를 기다리지 않는다.
3. 해당 PRD 항목 → 02의 공통 계약 → 09의 화면 상태 → 구현 이슈 순서로 연결점을 확인한다. 이름만 같은 별도 모델·잔액·파일 저장을 만들지 않는다.
4. 공유 계약 구현과 fixture가 아직 없으면 먼저 공통 기반 이슈를 수행한다. 문서 예제가 실행 가능한 fake라는 뜻은 아니다. 계약 변경이 필요하면 영향받는 담당과 조율하고 같은 PR에서 예제·호출자를 갱신한다.
5. 이슈에 담당·수정 파일을 알리고 작업 브랜치에서 구현한다. 구현자 기본 검증 → 다른 팀원 PR 확인 → 연결 기능 통합 시험 순서로 완료한다.

## 통합 순서와 검사

1. **공통 경계:** 모델/명령/오류 타입과 deterministic fixture, 단일 저장 거래를 먼저 연결한다. 저장 재시도·revision 충돌·버전 복원 시험을 통과해야 실제 재화를 쓰는 기능을 합친다.
2. **첫 세로 흐름:** 테스트 출처를 표시한 입력 → 의뢰/영업 하나 → 확정 결과 → 화면 조회 → 앱 종료/재실행을 연결한다. 최종 콘텐츠를 기다리지 않되 모의 실행을 차량 연동으로 표현하지 않는다.
3. **기능별 병렬 작업:** 필요한 연결점의 PR 검토와 해당 이슈의 착수 조건을 충족한 후, 합의된 인터페이스로 개별 계산·화면을 개발한다. B/C는 공통 조회/거래, A는 입력/도착, D는 화면 명령/결과를 맡는다. 기능 PR마다 관련 오류와 저장 영향을 검증한다.
4. **전체 회귀:** #28에서 동시 소비·지급, 제한 상태 전환, 저장 실패·재시작, 시간 경계·권한 거부·데이터 누락을 연결한다. 발견 결함은 해당 기능 담당에게 돌린다.
5. **제출 고정:** #29에서 소스 커밋·APK·영상·기획서·출처·접근권·익명 조건을 같은 버전으로 확인한다. 최종 전송은 별도 지시가 필요하다.

구현자는 이슈/PR에 `:core:test`, 앱 변경 시 `:app:assembleDebug :app:lintDebug`, 필요한 instrumentation 결과를 남긴다. 실제 명령·도구는 05, 결과는 06, 사람 리뷰/머지 규칙은 CONTRIBUTING을 따른다.

## 단계와 일정

M0는 환경·조사, M1은 계약·기획·화면, M2는 기능 구현, M3는 통합·제출이다. 단계는 전체 직렬 진행을 뜻하지 않는다. 공식 일정은 [공모전 안내](contest/01_CONTEST_GUIDE.md)에서 확인하고, 팀 목표일은 아직 미정이다. 1차 공식 의무와 팀의 완성 목표를 구분한다.

## 기존 이슈 이력

2026-11-03 #3–#10의 상위 묶음은 실행 가능한 작업으로 분리했고 #14의 잔여 결정은 #24/#25로 이동했다. 과거 #11 코드 조사와 기존 테스트 결과는 보존한다. 2026-11-04 사용자 요청에 따라 준비 결과에서 네 파트 상세 구현 이슈로 연결하고 독립 누락 검토를 수행한다. 결과 이슈 링크는 아래 기능 대응표에 기록한다.

차량 검증은 [검증 문서의 플랫폼 검증 인계](06_VERIFICATION.md#플랫폼-검증-인계)에서 완료된 에뮬레이터 근거와 실제 연결 단계의 선행 검증을 구분한다.

## 기능과 구현 이슈 대응

구현 이슈는 OMX `plan`으로 분해하고 별도 Critic이 전체 본문을 PRD와 대조했다. 타입 계약의 구체화·실제 기능 연결 완료 조건을 보완했고 순환 의존·담당 매핑을 확인했다. 이는 AI 계획 검토이며 사람 승인·기능 구현 검증이 아니다. 미정 기능은 구현 이슈의 시작 조건 또는 후속 생성 조건에 표시한다.

## 실제 선행조건과 차단 해제

기능 묶음의 나열은 직렬 착수 순서가 아니다. 별도 묶음 종료 대신 소비하는 데이터·명령·조회·화면 연결점이 필요하다. 예를 들어 #37 후보 생성은 목적지·거리·콘텐츠로 시작하고 #38은 #37의 선택 의뢰를 사용한다. #53의 fixture 화면도 실제 차량 지급을 기다리지 않는다. 실제 차량 지급·조회가 필요한 #39는 #46의 결과를 확인한다. #41은 탁송 전체 검증이 아닌 #46의 조회·점유 경계를 사용한다. #47·#48·#50은 렌터카 전체 검증 없이 #46과 해당 계약으로 진행한다. #49의 사고 결과는 #42, #42의 배정 입력은 #41 등 실제 관계는 유지한다.

화면 작업은 #51의 공통 탐색·조작 제한 연결점을 확인한 범위에서 진행한다. A/B/C의 실제 명령이 준비되기 전에는 합의한 fixture로 화면을 만들 수 있지만 실제 저장·지급 연결 완료로 닫지 않는다. #51의 PR #93 신호 소비 경로는 main에 있으므로 같은 연결을 다시 만들지 않고 미확인 실행 조건을 검증한다.

PR이 main에 머지되거나 필요한 결과가 검토·인계되면 담당자는 후속 이슈의 Blocked by와 본문을 대조한다. 실제 충족한 관계만 해제하고 근거를 남긴다. 다른 차단 관계와 정책·계약·결정 대기가 없으면 ready를 붙이며, 부분 인계로 이슈 전체를 자동 종료하지 않는다. #28은 준비된 시나리오부터 실행하고 전체 기능 종료를 일괄 착수 조건으로 요구하지 않는다. README의 임시 담당표도 함께 갱신한다.
