# 차량 성장 콘텐츠 기획

작성·확인: 2026-11-03 (KST). 이번 작업 범위: **문서와 조사 CSV 정리만**. 앱 코드·보상 로직·화면·자산은 수정하지 않았다.

## 1. 기준과 결정 이력

기획 원본: [드라이브 키우기 게임 기획서](공모전/드라이브키우기_게임기획서.pdf), 2026-11-03판 8쪽. 원본 PDF는 보존한다. 사실 목록은 [차량 조사 CSV](data/vehicles.csv) 한 곳에 둔다.

| 순서 | 사용자 결정 | 현재 적용 |
|---|---|---|
| 초기 추가 지시 | 별도 캐릭터 대신 차량 자체 성장, 같은 차종 유지 | 이후 차종 교체 결정으로 변경됨 |
| 업데이트 기획서 확인 후 최종 답변 | ‘새 기획서처럼 다른 차로 바뀜 — 캐스퍼에서 아반떼, 제네시스로’ | **현재 기준: 성장에 따라 다음 차종을 받는 구조** |
| 이유 명시 | 차종 조사는 다음 차로 바뀌는 게임을 만들기 위한 것 | 조사 목록을 성장 단계·세부 모델 검토에 연결 |
| 작업 범위 | 이번에는 문서만 수정 | 코드·목업·이미지·런타임 데이터 생성은 이번 범위 아님 |

최신 합의가 과거의 ‘같은 차종 유지’를 대체한다. 새 PDF에 있는 모든 초안 수치나 경제 시스템까지 이 선택 하나로 확정된 것은 아니다.

## 2. 차량과 캐릭터의 역할

- **확정:** 차량은 성장의 핵심 보상과 시각적 진행 주체다. 성장하면 현재 차종에서 다음 차종으로 교체된다. 차량 조사 목적도 이 단계 구성이다.
- **원안:** 르르르는 뚜벅이에서 운전을 배우는 이야기의 주인공·동승자다. 차량 단계와 병행하는 이야기 역할로 새 PDF에 유지되어 있다. 캐릭터 설정·디자인·권리·1차 포함은 별도 확정이 필요하다.
- **원안/미확정:** 같은 단계 안의 세부 모델·색상 수집과 가챠. 다음 차종으로 진행하는 것과 보유 도감·확률형 수집은 별개이며 후자를 1차 필수로 자동 추가하지 않는다.
- **확장/미확정:** 실제 탑승 차종과 게임 차량을 연결하는 기능. 차량 데이터 입력과 실제 차종 식별은 다른 기능이다. 실제 타는 차와 게임 속 차가 같아야 한다는 전제는 두지 않는다.

차량 교체는 **게임의 진행 설정**이지 실제 자동차의 진화·성능 개선·구매·소유 증명이 아니다. 르르르의 현실 설정·사용 허가는 이번 차종 조사로 확인된 사실이 아니다.

## 4. 최초 지급과 해금

| 항목 | 원안 | 현재 결정 상태 |
|---|---|---|
| 최초 플레이 상태 | 뚜벅이, 튜토리얼 후 스케이트보드 | 원안; 1차 데모 시작 상태는 미결정 |
| 첫 자동차 | 캐스퍼 | 대표 후보; 실제 첫 지급 확정은 아님 |
| 다음 차종 | 레벨 구간 도달 시 다음 차량 출고 | 차종 교체 방향 확정; 레벨 구간·누적 EXP 기준안 작성됨 |
| 경험치 | 주차 후 정산 | 흐름 확정; 성장 공식 작성·산술 검증됨. 일일 상한·보너스 포함 범위·최소 기록 조건은 보완 필요 |
| 세부 모델·색상 | 무료 가챠·도감 | 초안/확장; 1차 필수 아님 |
| 기존 차 보유 | 교체 후 보관·재선택 여부 | 원안에서 명확하지 않음; 보유 데이터 만들기 전 결정 |

PDF의 레벨표·누적 경험치·보상·가챠 확률·천장·시즌 수치는 이미 작성된 기획 기준안이다. [방치형 게임 적용 문서](idle-game-application.md)의 5~6절과 [제품 문서의 수치 확인 결과](PRODUCT.md#수치-확인-결과)를 참조하며, 같은 표를 이 문서나 사실 CSV에 중복 작성하지 않는다. 성장 공식과 단계 진입 누적 EXP의 산술 일치는 확인됐고, 도달 일수는 주행량 가정에 따른 추정이다. 기존 수치를 처음부터 다시 정하는 대신 일일 상한·보너스 중복 계산 여부·가챠 보장 카운터 등 비어 있는 규칙을 보완한다. 실제 성장 속도 검증과 최종 밸런스 확정은 별도이며 현재 코드의 시험용 수치를 기획 기준안으로 대체하지 않는다.

## 5. 핵심 흐름과 성장 전후 변화

1. **주차·조작 허용 상태:** 현재 차종과 진행 상태 확인. 미정 퀘스트·가챠를 필수 화면으로 만들지 않는다.
2. **주행 시작:** 게임 조작과 성장 연출을 닫고 기록 모드로 전환. 기록 가능 여부와 입력 출처를 구분한다.
3. **주행 중:** 사용자 행동 요구 없이 허용된 데이터만 수집한다. 차종 교체·보상·희귀 획득 팝업을 띄우지 않는다.
4. **주차 확인:** 기록의 유효성·중복 여부를 확인하고 정산한다. 기록 부족은 ‘확인 불가’로 표시하며 완벽한 안전운전으로 판정하지 않는다.
5. **정산:** 경험치와 진행 변화 확인. 확정된 해금 조건을 만족할 때만 다음 차종 지급 및 교체.
6. **차고 복귀:** 새 차종과 이력 확인. 별도 조작 없이 다음 주행에서도 선택 상태를 일관되게 유지한다.

| 상황 | 성장 전 | 성장 후 | 상태 |
|---|---|---|---|
| 같은 단계 내 성장 | 현재 차종·진행도 | 진행도/레벨 변화 | 세부 표현 미정 |
| 다음 단계 도달 | 현재 차종 | 다음 차종의 이름·외형으로 교체 | 구조 확정, 연출 미정 |
| 꾸미기 획득 | 기본 외형 | 색상·장식 등 변화 가능 | 후보; 확정 보상 아님 |
| 르르르 이야기 | 기존 이야기 장면 | 다음 장면·반응 후보 | 권리·디자인·범위 미정 |

이전 차종을 새 차종처럼 변형해서 보여주는지, 차고에서 교체하는지, 출고 연출을 쓰는지는 미결정이다. 차체 이미지와 이름을 함께 바꿔 다른 차종으로 진행했다는 점이 읽히게 한다. 가짜 숫자를 실제 제원처럼 표시하지 않는다.

## 6. 차종별 차이와 공통 규칙

차종별 차이는 확인된 이름·차체·외형·이야기 단계 및 승인된 아트에 둔다. 크기나 동력 방식에 맞춘 외형 차이는 가능하지만, 기능 지원은 실제 차량 입력의 Capability로 판단한다.

공통 규칙:

- 현실 가격·출력·최고속도에서 게임 등급·보상 배율·안전운전 점수를 자동 계산하지 않는다.
- PDF의 ‘가격순 차종’은 미확정 순서 제안이며 가격 수집으로 능력치 표를 만들지 않는다.
- PDF의 ‘더 높은 차종 → 공격력 상승’은 현재 미채택 검토 항목이다. 전투가 필요하다면 게임 성장값과 실차 성능을 분리해 다시 결정한다.
- 차종을 교체해도 동일한 기록에 다른 안전점수·XP가 적용되어서는 안 된다. 게임 레벨을 안전 자격으로 표시하지 않는다.
- 수소차·전기차·고성능차·고가차를 안전하거나 우월한 운전의 증거로 취급하지 않는다.
- 주차 확인·중복 지급 방지·기록 누락·재시작 정책은 모든 차종에 동일하게 적용한다.

## 7. 화면별 표현

새 PDF는 차고·수련·정산 3화면을 제시한다. 현재 구현에는 홈·차고 구분이 관찰되어 아래는 두 구조를 연결한 문서다. 화면 수를 새로 확정하거나 코드를 수정한 것은 아니다.

| 화면 | 표현할 정보 | 제한·미결정 |
|---|---|---|
| 홈 | 현재 차종·진행 상태·최근 정산 요약 | 차고와 통합 여부 미정. 추가 주행 유도 문구 금지 |
| 수련 | 기록 상태, 입력 이상 여부 | 게임 조작·진행 바 경쟁·차종 해금 연출 없음. 정지 그림도 플랫폼 허용 확인 필요 |
| 정산 | 이번 기록·지급 결과·진행 변화·조건 충족 시 다음 차종 | 반복 진입으로 중복 지급 금지; 정산 시 차종 교체 연출 |
| 차고 | 현재 차종과 승인된 외형 | 보유 도감·이전 차 재선택·가챠·꾸미기는 확정 전 비필수 |

운전 중 0km/h 또는 브레이크 ON만으로 게임 UI를 허용하지 않는다. 주차와 플랫폼 `CarUxRestrictions` 등 실제 제한 상태를 함께 판단한다. 데이터 부재 시 게임 조작을 허용하는 방향으로 추정하지 않는다. [기존 차량 API·설계 조건](공모전/03_차량_API와_설계조건.md) 5절 참조.

## 8. 불필요한 주행·위험 행동 유인 검토

새 PDF의 안전 의도와 충돌할 수 있는 부분을 남겨 둔다. **아래는 보완 제안이며 수치·산식을 확정한 것이 아니다.** 원본을 몰래 수정하거나 기능을 완료했다고 표시하지 않는다.

| 원안 위치·내용 | 문제 | 보완 방향 |
|---|---|---|
| 3~4·6쪽: 하루 30km 가정, km당 경험치, 몇 주 후 다음 차 | 목표 때문에 더 운전할 수 있음 | 평소 이동만 대상으로 하고 추가 거리로 성장 이익이 계속 늘지 않는 정산 규칙 검토 |
| 6쪽: 장거리 100km·출퇴근 연속일·주간 100km | 주행 의무·스트릭 손실 유인 | 비운전일 손실·최소 거리 해금 제거, 주차 중 안내 확인 등 대안 검토 |
| 7쪽: ‘오늘 드라이브 어때요?’·주말 보너스 | 불필요한 출발 유도 | 문구·시간대 이동 보상 미채택. 기존 이동의 정산 표현만 변경하는 안 검토 |
| 2·7쪽: 날씨 보스·한정 아이템 | 위험한 날씨 운전 동기 | 날씨에 따라 희귀 보상이 유리해지는 구조 제외 검토 |
| 2·7쪽: 급제동 HP 감소·피격 음성 | 필요한 긴급제동을 회피할 수 있음 | 회피 불가능한 사건을 벌하지 않기; 즉시 게임 감점·피격 반응 미채택 검토 |
| 2·6쪽: 차로 변경·기능 켜기 보상 | 불필요한 조작 유도 | 운전 행동 수행을 해금 필수 조건으로 만들지 않기 |
| 2·6쪽: 휴게소 방문 보상 | 우회·방문 반복 유인 | 휴식은 게임 외 안전 안내로 분리하거나 동등한 주차 휴식 인정 검토 |
| 4~5쪽: 확률형 수집·시즌 한정 보상 | 마감 전 반복 운전 유인 | 1차 필수 제외; 채택 시 비운전일 불이익·추가 주행 이익 검토 |

일일 상한 하나만으로 이런 유인이 해소됐다고 판정하지 않는다. 구체적 산식·최소 표본·미지원 기능 처리·백그라운드 실행은 팀 결정과 플랫폼 시험이 필요하다. 주행 중 기록을 구현할 수 있다는 가정과 실제 SDK 지원·승인은 별개다.

## 9. 대표 차종 하나로 먼저 검토할 것

**1차 시각 검토 후보: `hyundai_casper`.** 새 원안의 첫 자동차이므로 출고·단계 진입 장면을 검토하기 좋고, 세대·동력 혼동을 피하기 위해 일렉트릭과 구분할 수 있다. 낮은 가격·출력이 낮은 게임 등급의 근거라는 의미는 아니다. 최종 선택과 외형은 팀 확정 전이다.

이번에는 문서만 요청했으므로 시안·이미지·목업을 제작하거나 시각 검증을 완료하지 않았다.

후속 검토 순서:

1. 해당 차종의 연식·트림·외형 식별점과 자산 사용 조건 확인.
2. 같은 자산 하나로 기본 상태·레벨 변화·꾸미기 후보를 비교하고 홈·정산·차고에서 가독성 확인. 그림체·카메라 각도·색감은 미결정.
3. 다음 차종 해금은 우선 텍스트/중립 자리표시자로 흐름만 검토. 다른 차종 전체 자산을 동시에 제작하지 않음.
4. 첫 차 스타일과 화면 배치가 검토된 뒤 두 번째 차종을 제작해 실제 교체 전후 차이가 읽히는지 확인.
5. 수련 화면에서 조작·획득 유혹이 생기지 않는지 별도로 검증.

한 차종 자산만으로 여러 실차 사이의 시각적 차이까지 검증됐다고 보고하지 않는다. 초기 자리표시자는 실제 캐스퍼 자산으로 부르지 않는다.

## 10. 구현 연결과 기존 코드 관찰

작업 도중 Kotlin/Gradle 기반 `app`·`core` 파일이 추가된 것을 확인했다. 다른 작업자의 변경이며 이번 작업은 수정하지 않았다. 현재 읽은 `DashboardView.kt`는 임시 차량 도형·차량 레벨·첫 성장 배지를 표현하고, `DriveEngine.kt`는 시험용 정산 로직을 가진다. **다음 차종 지급·전환, CSV ID 연동, 정식 아트가 구현됐다는 뜻은 아니다.** 코드에 있는 수치를 최종 게임 규칙으로 역확정하지 않는다.

프로젝트 공통 기준은 [제품 요구사항](PRODUCT.md), [기술 계약](ENGINEERING.md), [검증 상태](VERIFICATION.md)다. 작업 중 세 문서가 추가되어 읽었으며 차량 성장 방향은 제품 문서와 연결한다. 본 문서는 차량 단계·자산·미결정 사항의 상세 근거이고, 차종 목록은 CSV 한 곳에서 관리한다.

구현 전에 정할 최소 필드 **후보**:

| 분리할 데이터 | 후보 필드·관계 |
|---|---|
| 차량 사실 | CSV의 `vehicle_id` 참조. 필요하면 세대·파생형을 분리 |
| 성장 단계 | 단계 ID, 대표 `vehicle_id`, 다음 단계 참조, 승인된 해금 규칙 참조 |
| 사용자 성장 | 현재 단계·현재 차량 ID·성장값·정산 처리 이력 |
| 표현 | 차량 ID와 승인된 아트 연결, 정산/차고 표시 상태 |
| 선택 확장 | 이전 차 보유·색상·수집 이력은 확정 후 추가 |

차량 역할은 차종 교체 성장으로 정해졌고 단계 순서·레벨 해금·경험치 수치의 기준안도 있다. 스타리아·제네시스의 대표 모델, 교체 후 보유, 미기재 보상 규칙은 보완이 필요하다. 이번 요청은 문서 작업이므로 런타임 JSON/Kotlin 콘텐츠 표를 만들지 않는다. 구현 시 기존 기준안과 보완된 규칙을 Kotlin 프로젝트에 필요한 최소 정적 데이터로 옮기고, 문서·코드·화면에서 같은 `vehicle_id`를 쓴다. 화면에는 읽기 쉬운 표시명을 사용하고 내부 식별자와 연결한다. CMS·관리 서버를 새로 만들지 않는다.

## 11. 1차와 이후 범위

- **현재 확정 방향:** 차량 단계 성장, 다음 차종 교체, 주행 중 게임 조작 없음, 주차 후 경험치·성장 결과 확인.
- **1차 제안:** 대표 한 차종의 시각 스타일과 정산 흐름부터 검토. 차종 교체 기능을 시연할 범위는 첫 자산 검토 후 정한다.
- **작성된 기준안:** 최초 지급·탈것 프롤로그, 단계 순서·레벨·XP·해금 수치, 보상·가챠·시즌 수치. 기존 PDF와 적용 문서를 기준으로 검토하며 처음부터 다시 기획하지 않는다.
- **추가 결정·확인:** 데모 시작 단계, 스타리아·제네시스 대표 모델, 일일 상한·보너스 포함 범위·가챠 보장 카운터, 교체 후 보유, 기능별 구현 범위, 자산 권리, 화면 스타일. 실제 성장 속도와 최종 밸런스는 미검증이다.
- **후속 확장 후보:** 세부 차종·색상 수집, 가챠, 시즌, 온라인 도감·랭킹, 실제 탑승 차종 연동, 상용차·다른 브랜드. 현재 필수 기능으로 추가하지 않음.
